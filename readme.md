# Patrones creacionales

Los **patrones creacionales** organizan la forma en que se crean los objetos. Su finalidad es separar los detalles de
construcción del código que utiliza esos objetos, para que sea más fácil cambiar una implementación, reutilizar
configuraciones y controlar cómo se obtienen las instancias.

Cada patrón responde a una necesidad distinta: **Builder** construye paso a paso; **Factory Method** delega la elección
del producto a subclases; **Abstract Factory** crea familias compatibles; **Prototype** copia un objeto existente; y *
*Singleton** controla el acceso a una instancia compartida. **Factory Function**, incluida en este curso como técnica de
creación, encapsula en una función la obtención de objetos o de otras funciones.

Son útiles cuando la creación empieza a repetirse, requiere varias decisiones o debe seguir reglas específicas. No hace
falta aplicar una fábrica a cada constructor: conviene elegir el patrón que resuelva una necesidad concreta.

## Detalles para entender los ejemplos creacionales

- **Prototype: copiar no equivale a asignar una referencia.** Si se escribe `copia = original`, ambas variables apuntan
  al mismo objeto. Con `clone()` se obtiene otro objeto. En este proyecto, `super.clone()` realiza una **copia
  superficial**: copia los valores de los campos y las referencias, sin duplicar recursivamente los objetos
  referenciados. Los campos de `Document` son `String`, que es inmutable; cambiar el título de la copia mediante su
  setter no cambia el título del original. Si se agregara una lista mutable, ambos documentos compartirían esa lista
  salvo que también se copiara. Prototype también puede implementarse con un constructor de copia o un método propio; no
  exige utilizar `Cloneable`.
- **Singleton: instancia compartida y concurrencia son asuntos distintos.** La sincronización de `getInstance()` protege
  el acceso a la creación en ese método, pero no vuelve automáticamente seguras todas las operaciones del objeto. La
  implementación del proyecto puede reemplazar la instancia cuando la conexión se cierra; las referencias anteriores no
  desaparecen por ello. El alcance habitual del campo estático en Java es la clase cargada por un mismo cargador de
  clases, no varias aplicaciones o servidores. Para aplicaciones reales con múltiples solicitudes, normalmente se
  administra JDBC mediante un `DataSource` y un pool de conexiones, en lugar de compartir una única conexión.
- **Factory Function y Factory Method tienen mecanismos distintos.** En el ejemplo funcional, una llamada como
  `LogFactoryFunction.apply("error")` obtiene un formateador; después, `formateador.apply("Falló la operación")` produce
  el mensaje. Factory Method utiliza subclases que sobrescriben un método de creación. Factory Function no forma parte
  de los 23 patrones clásicos de GoF, aunque es una técnica útil de creación que se estudia en este repositorio.

# Patrones estructurales

Los **patrones estructurales** definen cómo se relacionan y combinan las clases y los objetos para formar estructuras
flexibles. Su finalidad es facilitar la colaboración entre componentes, reducir dependencias innecesarias y permitir que
el sistema crezca sin multiplicar clases por cada combinación posible.

En estos ejemplos, **Adapter** permite utilizar servicios con interfaces diferentes mediante un contrato común; **Bridge** separa dos dimensiones que deben evolucionar de forma independiente; **Composite** representa elementos y
agrupaciones en un árbol; y **Decorator** agrega funcionalidades a un objeto mediante envoltorios combinables.

La composición consiste en que un objeto contiene referencias a otros objetos y les delega parte del trabajo. Por
ejemplo, una notificación puede contener un canal de envío, una carpeta puede contener archivos y otras carpetas, y un
decorador puede contener la notificación que amplía.

## Cómo distinguir los patrones estructurales

- **Adapter cambia la interfaz disponible para el cliente.** Permite aprovechar un servicio existente aunque sus métodos
  sean distintos de los que necesita la aplicación.
- **Bridge separa dos dimensiones del diseño.** En las notificaciones del proyecto, el tipo de notificación y el canal
  son independientes. Puede agregarse un nuevo tipo sin implementar otra vez todos los canales.
- **Composite organiza un árbol.** Una carpeta contiene archivos y otras carpetas; llamar a la operación del grupo
  permite recorrer sus componentes. La interfaz compartida corresponde a la operación común: no obliga a que una hoja
  admita agregar hijos.
- **Decorator organiza capas de comportamiento.** Cada envoltorio conserva el contrato del componente y añade una
  responsabilidad. En el ejemplo, la notificación acumula el comportamiento base, SMS y email. El orden de los
  envoltorios puede afectar el resultado o la secuencia de ejecución.
- **Bridge y Decorator usan composición con fines diferentes.** Bridge conecta dimensiones independientes, como tipo de
  notificación y canal. Decorator permite apilar responsabilidades alrededor de un objeto, como varios mecanismos de
  notificación.
